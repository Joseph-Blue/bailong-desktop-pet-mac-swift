# 原生版启动闪退调查与修复

日期：2026-10-29。故障版本：`0.1.0-dev.1`（`bf064e4`）；修复版本：`0.1.0-dev.2`。目标工程：`bailong-desktop-pet-appkit`。

## 结论

此次闪退来自历史列表刷新和选中通知的同步递归，导致主线程栈溢出。调查开始时未发现桌宠、FFmpeg 或桌宠自有 app-server 的残留进程，没有证据将此次故障归因于残留进程或实例锁。

## 证据与触发路径

系统 `~/Library/Logs/DiagnosticReports` 中，18:24—18:26 的 6 份 `BailongPet` 报告均属于 `com.bailongpet.appkit`，异常为 `EXC_BAD_ACCESS / SIGSEGV`，递归深度 1223—1224。最近一份为 `BailongPet-2026-10-29-182626.ips`；18:24:17 的报告明确写出主线程栈因过度递归而耗尽。

启动时控制器从历史中选取最后一个内置对话，界面按倒序显示全部会话。当该对话不在首行时，`reloadData()` 对选中行的校正会先发送通知，随后应用又恢复目标行；原来这两类程序触发的事件都可能进入 `onSelect`，再次刷新整个列表：

```text
ChatController.refresh
  → ChatInterface.refresh
  → NSTableView 重载／选中通知
  → tableViewSelectionDidChange
  → onSelect
  → ChatController.refresh
  → …
```

[Apple 的选中通知文档](https://developer.apple.com/documentation/appkit/nstableview/selectiondidchangenotification)说明，表格选择变化后会发送通知；它并不只代表用户点击。崩溃栈和三个虚构会话的旧版复现共同确认了本项目中的循环。

## 修复

`Sources/BailongPet/ChatUI.swift` 将重载和恢复选择作为一次程序更新，期间不向控制器发送用户选择回调。真正的选择变化先更新当前会话 ID，再通知控制器。没有修改历史格式、清空会话、删除实例锁或批量终止系统进程。

增加 `Tests/HistorySelectionRegression.swift` 与 `scripts/check-history-selection.sh`，只使用虚构会话；可手动运行：

```sh
./scripts/check-history-selection.sh
```
